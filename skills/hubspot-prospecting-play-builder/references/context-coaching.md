# Coach the three Context fields

This is a writing framework, not a required verbatim template. Research establishes the facts; the client chooses strategic priorities. Avoid turning a broad website portfolio into a single unqualified promise.

## What does your company sell?

Collect: core offer, delivery/engagement model, suitable customers, selected Play scope, important inclusions/exclusions, and evidence-backed differentiation. Describe the business in ordinary language before introducing product terminology. Explain whether buyers purchase a subscription, project, product, managed service, or another model. Separate company-wide capabilities from the selected campaign's focus.

**Teach:** this field lets the agent choose the right offer and describe how the buyer can engage. Without scope, the agent may pitch irrelevant services or imply that everything is included.

**Ask only when missing:** Which offering should this Play prioritize? What can a buyer reasonably start with? Which capabilities or commitments must never be implied?

**Example pattern:** “We provide [offering] for [suitable buyers] through [engagement model]. It helps with [work situation]. For this Play, emphasize [selected scope]. [Meaningful boundaries].” Replace these planning placeholders with supported information in final copy; omit unknown assertions.

## What is your value proposition?

For each relevant buying role, develop:

1. Responsibility or decision the buyer owns.
2. Outcome the buyer wants, described concretely.
3. Mechanism: how this offer changes the work or decision.
4. Relevant, supported proof when available; otherwise omit it.
5. Message angle and boundaries: when to use it and what must not be assumed.

**Teach:** a value proposition should help the agent translate capabilities into a buyer-specific reason to respond. “Improve efficiency” is too broad to select an email angle. Adding a mechanism explains why the contribution is credible.

**Synthetic non-IT example:** A training provider offers manager workshops. An HR leader might care about a consistent onboarding process; an operations leader might care about supervisors handling routine decisions. Practice sessions and reusable conversation guides are mechanisms. Reduced turnover is not proven merely because training was delivered. The email should select the role-relevant outcome rather than list workshop modules.

**Ask only when missing:** What changes in the client's day-to-day work? Why would this buyer choose this approach? Which case result supports this particular outcome? What alternatives might already be working adequately?

Prefer a useful explanation over unsupported superiority. Preserve metric definitions, time windows, customer context, and limitations. An example customer result is not a forecast for a new buyer.

## What pain points does your company solve?

Map each useful pain as **work situation → symptom → plausible consequence → contribution → evidence needed before asserting it**. Separate symptoms from causes. Do not assume the current team is ineffective or the incumbent vendor has failed.

**Teach:** this gives the agent recognizable situations to investigate. It should connect a verified event to a possible problem, not diagnose the account from a headline.

**Synthetic example:** Several locations onboard managers differently. That can create inconsistent guidance; shared practice and materials may help. Opening new locations supports a question about consistency, not a claim of poor management or staff attrition.

**Ask only when missing:** What prompts customers to seek help? What do they try first? What operational consequence matters to the selected buyer? What would make this pain irrelevant?

## Review the fields together

Ensure the selected offer, target audience, outcomes, proof, and exclusions agree. Keep useful depth while removing duplicated slogans. A verified initiative or stated need should override generic persona assumptions. Put cadence, CTA rules, and length preferences in Outreach, not in every Context field.

Provide a brief “why this structure helps” note in the setup guide, then separate plain-text files with no coaching, source footnotes, internal notes, or unresolved placeholders. Keep source attribution in the evidence register. User-confirmed claims without documentation must retain that status there; do not manufacture an external source.
